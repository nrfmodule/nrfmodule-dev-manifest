## T3 — #208 (+#198): button click = locate now

Design locked with Vincent (grill 2026-08-12):

- Click (single tap) in ACTIVE / WAIT_BEGIN / SLEEP: battery blink (existing) + config poll + one-shot GNSS sample cycle + force-drain the queue when the sample lands. In DOCKED: battery cue only. A click while a click-cycle runs is ignored (no queueing).
- The SM is NOT touched: no new states, no new events. The click flow is a service-layer orchestrator; leaf semantics (timers, uploader mode) stay authoritative and the one-shot self-reverts.
- GNSS ownership rule: the click NEVER drives gnss_producer. It enqueues a one-shot cycle request INTO the sampler, which serializes all cycles on its own thread (do not become caller #6 of issue #159). `sampler_stop_sync()` cancels an in-flight one-shot exactly like a normal cycle.
- New: small orchestrator module (~150 lines, own .c/.h per file-organization rule); sampler one-shot request API; uploader force-drain/kick API. The uploader API + ~5 lines of shell = #198's force-send command: fold it in, close #198 in the same PR.
- Green LED cue on drain completion comes from T5 (no LED code here).
- Tests: orchestrator collision cases — dock event mid-cycle, begin-reached mid-cycle, click during ACTIVE (dedupe), stop_sync during one-shot, timeout without fix.
- HIL checklist: tap in each state; verify sleep/begin timers survive; location appears in app after tap.

## T5 — #204: LED language

Design locked with Vincent (grill 2026-08-12). Supersedes #61's 5-minute window (Damir's own revision). Post the design as a comment on #204 (done at planning time).

Vocabulary:
1. GPS searching: dim slow blue breathe (~2 s cycle, low PWM duty) while a GNSS session runs without a fix. Muted class. Power hit accepted for visibility.
2. Location fix: three quick blue blinks on fix acquisition, then one short blue blink per stored sample. Muted class.
3. Data sent: short green blink per successful POST (reads as a flutter during drains) + a ~1 s green success sweep when a drain that started at >=16 records reaches zero. Config poll success: single green blink. Muted class.
4. Boot show: ~2 s green sweep (always plays; mute cannot be active at boot).
5. Power-off: SOLID red from the moment shutdown is triggered (shell command, or long-press in gated builds) until the device actually dies. A state, not an animation. Survives mute.
6. Low battery: red double-blink on each battery tick (30 s) at LOW or worse. Warning class, survives mute.
7. Error, DFU phases, charging: existing layers, unchanged, survive mute (charging = external power, no energy concern).

Mute:
- `led mute` / `led unmute`: shell command + server command (config-poll command channel, same mechanism as sleep/begin). Add to the server-command allowlist file.
- Mutes classes 1-3 only. Reboot forgets the mute. Kconfig fallback: auto-mute after 30 min of continuous ACTIVE (default 30, 0 = never).

Implementation notes:
- Split the existing `led_indicator_activity()` (green, 5-min window) into the new cues; delete the window.
- Power-off red: ST_OFF entry sets the shutdown layer (today it sets LED off); the rail cut extinguishes it. Enum value added where `enum tracker_led` lives today (do NOT do #175's enum move in this PR).
- Observers: sampler (sample stored), uploader (POST ok, drain done), gnss_producer (session searching/fix), battery (tick + level). Follow the existing observer/allowlist pattern; no new singletons sprinkled.
- Tests: mute classification, fallback timer, drain-sweep threshold as pure logic. Visuals are HIL.
- HIL checklist: each cue visually; mute silences 1-3 and nothing else; reboot re-arms; `led mute` over BLE shell; power-off shows solid red through the quiesce.
